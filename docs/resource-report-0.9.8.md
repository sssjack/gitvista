# GitVista 0.9.8 资源治理与占用报告

测量日期：2026-09-27。平台：Windows x64。对比版本：本机已安装的 0.9.7 与本次生产构建的 0.9.8。

## 结论

GitVista 的主要固定体积来自 Electron 和内置 MinGit。源码、开发依赖、安装包、安装后的程序是不同口径，不能把开发机里所有历史产物加在一起，当作普通用户的安装需求。

本次修复重点是给持续增长的资源加上回收机制与容量边界，并移除发布包内重复的前端依赖。应用仍是 Electron 多进程软件，不承诺几 MB 内存，也不以短时验证代替长期稳定性测试。

## 运行内存实测

测试机器：AMD Ryzen 7 5800H with Radeon Graphics，16 个逻辑处理器，操作系统可见内存 13.86 GiB，Windows 内核 10.0.26200。两版均为 Electron 44.4.5，使用 GitVista 本仓库与相同显示缩放；大型数据另用独立压力用例验证。

**真实前台主窗口**：两版使用相同 1560 × 1000 内容区、DPR 1；每次采样前后确认页面可见，Windows 实际前台窗口属于该测试进程。各取 5 次样本。

| 版本 | 私有内存均值（MiB） | 私有内存最小–最大（MiB） | 工作集均值（MiB） | 应用进程数 |
| --- | ---: | ---: | ---: | ---: |
| 0.9.7 | 316.7 | 316.66–316.68 | 497.4 | 5 |
| 0.9.8 | 276.3 | 276.34–276.36 | 402.5 | 4 |

**另一次独立配置的后台流程采样**：Windows 将主窗口判为隐藏/被遮挡，因此下面的主窗口数据只作为后台数据，不作为前台低内存宣传。迷你窗口在流程中被打开，托盘阶段等待 70 秒。

真实前台主窗口私有内存均值降低 **40.3 MiB（12.7%）**。迷你窗口采用首次使用时创建，因此第一次打开它后，进程数会增加；关闭为托盘并不等于销毁所有 Electron 进程。各场景的工作集变化见表，不能把首次打开窗口的下降比例套用到所有使用状态。

原生采样同时确认：托盘阶段页面处于隐藏状态，已释放历史行；恢复后重新读取。两版所有场景均无页面脚本错误。

测量方法：直接启动生产 EXE，以其 PID 为根，通过 Windows `Win32_Process` 枚举所属 `GitVista.exe` 子进程，再用 `Get-Process` 读取 `PrivateMemorySize64` 和 `WorkingSet64` 后求和。包含主进程、渲染器、GPU 和其他 Electron 辅助进程；采样时 Git 读取已空闲，不包含短时 Git 子进程、开发服务器或其他桌面软件。

应用操作通过 CDP 的 `noDefaults` 模式执行；前台采样另通过 Windows 窗口 API 将测试窗口恢复并置前，再核对真实前台 PID。不使用 Playwright Electron 启动器，不模拟页面焦点，也不添加关闭后台节流的启动参数。前一轮自动化默认模式改变了页面可见性，因此那轮数据未用作上述结论。

- **私有内存**是进程已提交的私有内存，不等于此刻全部驻留在物理内存中的量。
- **工作集**是当前驻留内存；多个进程的工作集相加可能重复计算共享页面，不能直接当作全机净增内存。
- 设置页“应用内存”优先显示 Electron 提供的私有内存统计，属于另一时刻的即时采样，可能与任务管理器某一列不同。
- 两版使用各自独立的干净用户配置，同一个 GitVista 仓库，同一显示缩放。每个场景采样 5 次；连续切换历史提交 30 次，再测量迷你横条、托盘隐藏 70 秒及恢复主窗口。
- 这轮是单机短时场景对照，旧版先运行、新版后运行；系统文件缓存、垃圾回收、GPU 驱动和采样时机都会影响数字。不能据此证明 8 小时或多天运行“零泄漏”，也不能把小仓库采样当作所有大仓库的上限。

| 问题 | 本次处理 | 边界与保护 |

| 预览向真实仓库写入临时 Git 对象 | 预览使用独立对象目录，只读借用真实对象；结束时回收 | 执行提交前仍核对预览树和当前索引，避免审阅内容与提交内容不一致 |
| 提交成功后钩子超时，被误报成普通失败 | 检查 HEAD 是否已更新，返回已生成提交及明确提示 | 不自动重复提交；需要恢复时保留原索引并提示位置 |
| 快速切换导致过期读取和 Git 子进程积压 | 相同读取共享，过期订阅取消；取消最后一个订阅时结束所属进程树 | 不将独立提交或推送作为读取任务取消 |

主要实现位于 `electron/git-resources.ts`、`electron/git-transactions.ts`、`electron/resource-service.ts`、`electron/desktop-companion.ts`、`src/lib/resource-budget.ts`、`src/lib/text-pages.ts` 及 `scripts/`。

## 开发机为什么比安装后的程序大

`node_modules/` 保存编译器、Electron、打包器等开发依赖；`vendor/` 是打包使用的 MinGit 副本；`release/` 同时保留安装器、便携包和解压程序，三者本来就包含重复内容。用户安装后不需要保留整个源码工程。

`.local/` 中的浏览器配置、临时仓库、截图和压力测试样本属于本地验证数据，不会随 Git 推送，也不会进入安装包。本次新增统一验证入口：

```powershell
npm run validation:run -- smoke node .local/tests/smoke.mjs
npm run clean:artifacts -- -WhatIf
npm run clean:artifacts
```

新的验证脚本应把产物放到 `GITVISTA_VALIDATION_DIR`，维护程序才能识别归属。默认同组保留最近 1 次，结合 14 天期限和 512 MiB 总预算处理；活动运行和最近 2 小时的产物受保护，因此预算允许短期超出。未知命名的历史调试目录不会被猜测性删除。

npm、Electron、electron-builder、Playwright 的全局缓存可能被其他项目复用，不能全算在 GitVista 名下，也不由 GitVista 启动时清空。用户仓库的 `.git` 随提交和拉取正常增长，属于版本历史；本次避免预览制造额外对象，不激进删除真实历史来制造“瘦身”效果。

- **后端 16 项验证通过**：连续 100 次预览，真实对象数量与索引字节保持不变；覆盖部分暂存、审阅过期、SHA-256、linked worktree、钩子超时、恢复索引、查询共享、取消进程树，以及读取预算已满仍能完成独立提交。结束后活动/排队查询、Git 进程和读取缓冲计数全部归零。
- **缓存维护 7 项验证通过**：超过预算的缓存回收、配置和持久化存储保留、延迟维护、内存单位检查、拒绝标记与缓存目录联接。
- **安装与清理 38 项隔离验证通过**，另验证 PowerShell 模块兼容、真实 NSIS 辅助文件复制时序、未知附加文件保护及同版本差量清单维护。覆盖下载/构建失败保留上一份产物、版本排序、卸载越界与修改文件保护。
- **界面与数据规模验证通过**：100 个仓库、10,100 条提交的前后翻页；100,001 行源码内容还原；大 Diff 原始内容和行号保持；迷你窗口 100,005 行补丁最多绘制 400 行且末页可访问。筛选、历史第 4 页、滚动位置和提交草稿经过暂停/恢复验证。

- **验证边界**：程序运行测试使用实际生产解压程序。NSIS 完成实际编译，安装/卸载保护逻辑在隔离目录验证；本轮没有在用户正式安装目录执行系统级安装器升级/卸载，也没有进行全天耐久测试。

测试脚本、测试目录和原始运行产物只保留在本地，未纳入 Git 提交。仓库保留这份汇总报告，便于使用者知道验证范围；安装包及开发依赖也不进入源码提交。

## 后续可做的验证

建议后续在有大量历史、超大 Diff、网络慢或频繁切换仓库的真实工作流中，进行数小时驻留测试，观察私有内存回落、句柄数、Git 子进程数和缓存大小。若需要持续性能门禁，可用本次场景作为基线，并加入多仓库、凭据交互和异常关机后的恢复用例。本轮未实施全天耐久测试，不据此宣称彻底消除所有可能的资源增长。
